What it is

Everything an agent needs to call your APIs, kept where your code already lives.

A lightweight API discovery tool for agents and humans. It indexes the services your org runs, and the agents that already work in those repos keep it accurate.

Local + git first

One small binary on your machine. Contracts, docs and flows are plain files in git, reviewed like any other change. Use it from whichever door fits the moment.

  • CLI
  • UI
  • MCP

Business-first docs, written by agents

Add Sapien to a service and its coding agent writes the docs that matter: when to call an operation, what must exist first, what it changes, which errors are normal. Alongside the OpenAPI schema and a sample payload for every request. Agents in other repos query it, and developers find it by intent.

Shared through free git workspaces

A team workspace is a git repo listing your services, environments, flows and memories. Clone it and you have everything your team has built. No seats and no sync service: it's just git.

No backend

Your data lives in your own git remotes and on your machine. There is no Sapien account, no Sapien server, and nothing phones home. Secrets stay in your OS keychain.

Who it's for

One catalog, four very different days.

The same docs, examples and flows serve whoever is asking: the person who owns the service, the people who call it, and the agents doing both.

Backend developer

Where Sapien started

“Agentic coding made development very fast, but dev testing in a microservice architecture became the bottleneck. Checking one change meant hand-crafting calls across three services to see whether the journey still worked. Flows have become a lifesaver.”
  • Describe the journey once; the agent writes the flow across every service involved.
  • Rerun it after every change. A failure names the step, the request and the response.
  • Resume from the failed step instead of starting over, then promote the flow so the whole team gets it.
$ sapien flow run refund-reverses-ledger --env stage
$ sapien flow run refund-reverses-ledger --env stage \
    --resume <run-id>        # from the failed step

UI engineer

Building against services they don't own

The problemThe screen needs an endpoint. Which one, what goes in the body, and which errors should the UI handle? The answer lives in a repo you don't have checked out.

  • Search by intent in the browser (“refund a payment”) and open a ready-to-send request in Try it.
  • Your agent in the frontend repo reads the backend's docs and payloads over MCP while it wires the screen.
  • Get test data from a flow instead of a Slack thread with the backend team.

QA engineer

Owning journeys that cross service lines

The problemCross-service regressions live in someone's head, or in a collection nobody updates when the API changes.

  • Journeys become flows with assertions, and polling where the system is asynchronous.
  • Every run keeps each step's request, response and timing, ready to attach to a bug.
  • Invariants the team records as memories become assertions in the next flow an agent writes. Run the suite in CI with JUnit reports.
$ sapien flow run checkout-happy-path --env stage \
    --report junit --out results.xml

Coding agent

Dropped into one repo, calling forty services

The problemIt can read the repo it's in. Everything that repo calls is a guess: operation names, payloads, and the rules nobody wrote in the code.

  • get_context and search_apis find the right operation by intent, across every service.
  • get_api hands back a request example that's ready to send, not a field list to guess from.
  • execute_api resolves base URLs, auth and secrets, records the run and diagnoses failures. What worked is saved with create_example for the next agent.
get_context("refund a captured payment")
get_api("refund-service.createRefund")
  → request_example, rules, normal errors
execute_api(…, env="stage")
  → 201, run recorded
create_example(run_id)
  → saved for the next agent

Install

From zero to an agent that knows your APIs in a few commands.

One static binary for macOS and Linux, on amd64 and arm64. The UI and the MCP server ship inside it.

  1. Install the binary

    $ curl -fsSL https://gs-sinha.github.io/sapien/install.sh | sh

    Detects your OS and CPU (an Apple silicon Mac under Rosetta still gets the native build), verifies the release checksum, and installs to /usr/local/bin, or ~/.local/bin when that isn't writable. Works with wget too. Pin a version with SAPIEN_VERSION=v1.4.1, or choose the directory with sh -s -- --prefix ~/bin.

    $ brew install gs-sinha/tap/sapien
    $ go install github.com/gs-sinha/sapien/cmd/sapien@latest

    Needs Go 1.25+. A binary built this way reports its version as dev.

    $ git clone https://github.com/gs-sinha/sapien.git && cd sapien
$ make build                                     # writes bin/sapien
$ ln -s "$PWD/bin/sapien" /usr/local/bin/sapien

    Windows isn't supported yet; run it inside WSL.

  2. Create a workspace

    A workspace is the folder that lists the services one system is made of. Start local; you can make it a team workspace later. Local or team?

    $ sapien init ~/sapien-workspace && cd ~/sapien-workspace

    After this first one, workspaces don't need a terminal: the inspector's workspace picker has Add workspace, which creates a new workspace, clones your team's workspace repo, or opens a folder you already have, then switches to it.

  3. Connect your agent

    Installs the Sapien MCP server for every Claude Code session on this machine, in any repo. Swap the client for codex, cursor or cowork (Claude Desktop), or use generic to print JSON for another host.

    --allow-mutations lets agents make POST, PUT, PATCH and DELETE calls, which running a flow that creates data needs. It applies to non-production environments on this machine only; production stays blocked. Leave it off and agents can only read.

    $ sapien mcp config --client claude-code --write --allow-mutations
$ claude mcp list                     # sapien: ✓ connected

  4. Open the UI

    The inspector is served by the local daemon, so there's nothing else to install: flows and their runs with every request and response, services and operations with intent search and Try it, examples, memories, and an Agent tab that runs your own claude or codex in a terminal.

    $ sapien ui                                # opens http://127.0.0.1:7717 in your browser
$ sapien ui --install-app                  # macOS: Sapien.app for Spotlight and the Dock

    Semantic search is off by default and isn't a setup step: turn it on anytime from the inspector's Settings page, which detects a local Ollama install, lists and pulls models, and applies live with no daemon restart, or run sapien semantic enable --kind ollama --model nomic-embed-text.

Workspaces

A workspace describes a system. It never owns the services in it.

Each service's contract and docs stay in that service's own repo. The workspace records which services belong together and where to read them, the environments to call them in, and the flows, memories and examples you build up along the way.

Keep one workspace per system: every service your team calls together, from however many repos. Search, context and flows all span a workspace, so splitting a system hides cross-service knowledge from your agents.

acme-workspace/
├── sapien.workspace.yaml        services and their sources
├── environments/                base URLs and auth
├── flows/ memories/ examples/   shared with the team
├── local/                       this machine only
└── sapien.workspace.local.yaml  your checkouts, gitignored

Local workspace

A folder on your machine.

  • Services are paths to checkouts you already have.
  • Flows, memories and examples stay on this machine.
  • Nothing to set up beyond sapien init.

Best for trying Sapien, solo work, or a system only you touch.

Team workspace

The same folder, committed as a git repo your team clones.

  • Services are git sources (repo and branch), fetched every ten minutes. Nobody needs every repo checked out.
  • Bind a service to your own checkout to work on it; what you write about it rides your pull request.
  • New flows, memories and examples start local, and you promote and push the ones worth sharing. Sapien never pushes on its own.

Best for teams and new hires. It's free: it's just a git repo.

  1. Create it

    $ sapien init ~/sapien-workspace && cd ~/sapien-workspace

    Or in the inspector: workspace picker → Add workspace → New. Pick the parent folder in the folder browser, name it, optionally tick git init, and it is created, registered and opened.

  2. Add the services you have checked out

    A service needs an api/ package. If it doesn't have one yet, onboard it with an agent first.

    $ sapien service add ~/code/payment-service
$ sapien service add ~/code/ledger-service

  3. Set up environments

    Scaffold environment files from what the services declare, fill in auth, store secrets in your keychain, and check each service answers.

    $ sapien env scaffold
$ sapien secret set STAGE_TOKEN --stdin
$ sapien env probe stage

  4. Connect your agent and open the UI

    $ sapien mcp config --client claude-code --write --allow-mutations
$ sapien ui

A team workspace is a local workspace committed to its own git repo, with every service listed as a git source so anyone who clones it can read them. Commit the workspace and add a remote before you add services: that's how Sapien knows it's shared.

  1. Create the workspace and push it to an empty repo

    $ sapien init ~/acme-workspace && cd ~/acme-workspace
$ git init -b main && git add -A && git commit -m "Sapien workspace"
$ git remote add origin git@github.com:acme/sapien-workspace.git
$ git push -u origin main

  2. Add services as git sources

    Give a repo URL, or the path to a checkout: Sapien records the checkout's origin as the team's source and binds your checkout on this machine. A service shows up for teammates once its api/ package is on the branch.

    $ sapien service add git@github.com:acme/payment-service.git --ref main
$ sapien service add ~/code/ledger-service     # records its origin, binds this checkout

  3. Scaffold environments, point your agent here, and share

    Environment files reference secrets by name. The values stay in each person's keychain, and the agent permissions in .sapien/ stay on your machine; neither goes into the repo.

    $ sapien env scaffold
$ sapien mcp config --client claude-code --write --allow-mutations
$ git add -A && git commit -m "Add services and environments" && git push

Clone the team's workspace and every service is searchable right away, read from the team's git sources. Then bind the services you actually work on to your own checkouts.

  1. Clone and register it

    $ git clone git@github.com:acme/sapien-workspace.git ~/acme-workspace
$ sapien workspace add ~/acme-workspace
$ sapien workspace use ~/acme-workspace     # the default outside any workspace

    Or without a terminal: in the inspector, workspace picker → Add workspace → Clone. Paste the repo URL, pick where it should live, and Sapien clones it, registers it and switches to it, with every service searchable as soon as it opens. Existing does the same for a clone you already have.

  2. Connect your agent and add your own secrets

    $ cd ~/acme-workspace
$ sapien mcp config --client claude-code --write --allow-mutations
$ sapien secret set STAGE_TOKEN --stdin
$ sapien ui

  3. Start work on a service: bind your checkout

    This machine now reads the service from your branch and re-indexes on every save. Docs, examples and flows about it are written into its api/ folder and ship in your pull request. sapien service unbind payment-service goes back to the team's version.

    $ cd ~/code/payment-service
$ sapien service bind .                     # the service is inferred from origin

  4. Stay in sync, and share what you built

    The UI's status bar shows when teammates' commits are waiting, and offers Pull and Push buttons too.

    $ sapien workspace pull                             # fast-forward only
$ sapien flow promote refund-reverses-ledger --commit  # local → team, one commit
$ sapien workspace push

Onboard a service

Your agent documents a service in one session.

Onboarding writes an api/ package into the service's own repo: the contract, business-first docs, and an example for every request body. You review it and commit it like any other change.

No docs yet? Ask your agent.

Open Claude Code, Codex or Cursor in the service's repo, or the Agent tab in sapien ui. The Sapien MCP server already tells it how to onboard a service, so either of these works:

What the agent does

  1. Reads get_dsl_reference("service") for the package layout and the rules docs must follow.

  2. Drafts api/ from the real code, never inventing endpoints, fields or status codes.

  3. Asks you one batched round of questions. Anything nobody can answer goes under “Open questions” instead of being guessed.

  4. Registers the service with add_service, then closes the documentation and example gaps it reports.

  5. Adds a Sapien section to CLAUDE.md or AGENTS.md, so the next agent that changes the code updates api/ in the same change.

api/
├── openapi.yaml   the contract, with request examples
├── service.yaml   owners, concepts, environments
└── docs/          overview.md + one file per area

payment-service: 12 operations, status ok
docs: 12/12 operations documented in api/docs
examples: 7/7 bodies have a request example

Already has a contract?

If the repo has api/openapi.yaml (with optional service.yaml and docs/), register it directly.

# a checkout on this machine
$ sapien service add ~/code/payment-service

# a remote repo, no checkout needed
$ sapien service add \
    git@github.com:acme/payment-service.git \
    --ref main --subdir api

# a contract that lives somewhere else
$ sapien service add ~/code/billing \
    --contract openapi/billing.yaml

  1. Run sapien ui and open Services.

  2. Use Add service: paste a checkout path or a git URL, with an optional name, ref, subdirectory or contract path.

  3. Read the warnings it shows, then open the service to see its operations, docs and coverage.

A contract alone makes a service findable. Docs make it usable. Every add reports how many operations the docs reach and how many request bodies have an example, so you know exactly what's left.

Flows

Multi-service journeys, from a prompt to a green run.

A flow is a YAML file of calls across services, with values passed between steps, assertions, and polling where the system is asynchronous. Agents write them. You run them from the terminal, the UI, or CI.

  1. 1get_context and search_apis find five operations across the payment, ledger and refund services.
  2. 2get_api returns a ready-to-send body for each, so nothing is assembled from a field list.
  3. 3get_relevant_memories surfaces the team's invariants and gotchas, which become assertions or polling.
  4. 4validate_flow until it's clean, then create_flow. New flows land in your local tier.
  5. 5run_flow reports every step. A failure is diagnosed, and patch_flow fixes one step without rewriting the file.

A flow that creates or changes data needs --allow-mutations from step 3 of Install. Environments marked production stay off limits to agents unless you grant that separately.

More prompts to try

refund-reverses-ledger.flow.yamlwritten by the agent

version: 1
id: refund-reverses-ledger
name: Refunding a captured payment reverses its ledger entry
inputs:
  customerId: { type: string, default: cust_8f21 }
steps:
  - id: create
    call: payment-service.createPayment
    body:
      customerId: "${inputs.customerId}"
      amount: 49900
      currency: INR
      method: { type: card, token: tok_test_visa }
    extract: { paymentId: body.paymentId }
    assert: [status == 201, body.status == "AUTHORIZED"]

  - id: capture
    call: payment-service.capturePayment
    input: { paymentId: "${steps.create.out.paymentId}" }
    extract: { entryId: body.ledgerEntryId }
    assert: [status == 200, body.status == "CAPTURED"]

  - id: entry
    call: ledger-service.getEntry
    input: { entryId: "${steps.capture.out.entryId}" }
    assert: [status == 200, body.state == "POSTED"]

  - id: refund
    call: refund-service.createRefund
    body: { paymentId: "${steps.create.out.paymentId}", amount: 49900 }
    assert: [status == 201, body.status == "REFUNDED"]

  - id: reversed
    call: ledger-service.getEntry
    input: { entryId: "${steps.capture.out.entryId}" }
    assert: [status == 200, body.state == "REVERSED"]
